# Implement From Ticket

Full ticket-to-PR lifecycle. Takes a Jira ticket key, reads the ticket and any linked
Confluence specs, plans the work, implements it, opens a PR, updates the ticket
status at each lifecycle event, and hands the ticket off to QA on merge.

**Prerequisites:**
- `.memory/JIRA_WORKFLOW.md` exists (generated by `setup-jira`). If missing, STOP
  and run `setup-jira` first.
- `.memory/TEAM.md` recommended for automatic handoff on merge.
- Atlassian MCP connected. If not, STOP and point the user to
  `docs/ATLASSIAN-SETUP.md`.
- Use the `atlassian-integration` skill for all MCP calls.

**Inputs:** Jira ticket key (e.g. `PROJ-1234`). The user triggers this with
*"Implement PROJ-1234"* or similar.

## Pre-Flight

- [ ] Read `.memory/RULES.md` — workflow conventions.
- [ ] Read `.memory/MAP.md` — current project structure.
- [ ] Read `.memory/SYMBOLS.md` — symbol index for impact analysis.
- [ ] Read `.memory/RESUME.md` — in-flight work to avoid conflicts.
- [ ] Read `.memory/LESSONS.md` — prior mistakes to avoid.
- [ ] Read `.memory/SACRED.md` — sacred behaviors not to be changed.
- [ ] Read `.memory/JIRA_WORKFLOW.md` — status transitions, auto-apply flags,
      handoff rules, branch naming pattern, required fields.
- [ ] Read `.memory/TEAM.md` (if present) — ownership map and QA assignments.
- [ ] Verify MCP connectivity via the `atlassian-integration` skill
      (`atlassianUserInfo`). Fail fast if disconnected.

## Phase 1 — Understand the ticket

- [ ] **Step 1:** Call `getJiraIssue(key)` via the `atlassian-integration` skill.
      Capture title, description, acceptance criteria, current assignee, labels,
      priority, and status.
- [ ] **Step 2:** Call `getJiraIssueRemoteIssueLinks(key)` to get linked Confluence
      pages and linked tickets.
- [ ] **Step 3:** For each linked Confluence page, call `getConfluencePage` and read
      the full spec content.
- [ ] **Step 4:** Present a brief summary to the user: "This ticket asks you to
      [X]. Linked spec: [title]. AC: [list]. Ready to plan?"
- [ ] If the ticket is unclear or missing AC:
  - [ ] Add a comment asking clarifying questions via `addCommentToJiraIssue`.
  - [ ] If a `Waiting` or equivalent status is configured, transition the ticket to
        it via `transitionJiraIssue`.
  - [ ] STOP and wait for clarification.

## Phase 2 — Plan

A Jira ticket describes *what* the user thinks should be built, not the *whole truth* of what the change touches. Tickets are written by humans who may not know the existing implementation, may miss edge cases, or may not realize they're requesting a significant logic change. **Do not implement the ticket text verbatim.** Walk through the three sub-steps below before drafting the plan.

### Step 2.1 — Existing implementation review (mandatory)

- [ ] Invoke the `codebase-navigator` skill to locate relevant files using MAP.md and SYMBOLS.md rather than re-scanning the tree.
- [ ] For each area the ticket would touch: read the current code. **Summarize the existing behavior in the plan** — what it does today, what assumptions it makes, what callers depend on it.
- [ ] Note any pre-existing bugs, dead code, or comments suggesting prior intent. Do not "fix" them as a side effect — flag them separately.

If the ticket conflicts with existing behavior (e.g. "add feature X" but X is partially implemented and broken), STOP and surface the conflict to the user before continuing. Do not silently extend broken code.

### Step 2.2 — Edge case enumeration (mandatory)

- [ ] From each acceptance criterion, derive edge cases. At minimum cover:
  - **Empty / null / missing inputs.** What happens when the input is absent?
  - **Boundary values.** Min, max, zero, negative, off-by-one.
  - **Error paths.** What can fail? What happens to in-flight state?
  - **Concurrency / races** (if the area touches shared state, async work, or DB writes).
  - **Backwards-compatibility.** Existing data, existing API consumers, in-flight sessions.
- [ ] List each edge case in the plan with the intended handling (`handled` / `not applicable` / `out of scope — flagged`).
- [ ] If the ticket has no acceptance criteria, **STOP** — add a comment to the ticket asking for them via `addCommentToJiraIssue` and wait.

### Step 2.3 — Significant-change gate (mandatory)

A change is **significant** if any of these are true:
- Alters **>30 lines** of existing logic (not counting whitespace / comment / pure-add lines).
- Removes or replaces a **documented behavior** (described in a doc comment, README, or wiki).
- Changes a **public API signature** (function exported across modules, REST endpoint, schema).
- Touches anything listed in `.memory/SACRED.md`.

For each significant change identified, write a `SIGNIFICANT CHANGE: <one-line description>` row in the plan with: what changes, what depends on the old behavior, and the migration / rollout plan if any.

After presenting the plan, **wait for a separate explicit confirmation** of any `SIGNIFICANT CHANGE` row before proceeding to implementation. Initial plan approval does **not** authorize significant changes — they require their own gate. This is intentional friction: the most common failure mode is shipping a ticket-driven change that quietly broke an unrelated contract.

If the user says "proceed as planned" without specifically acknowledging the SIGNIFICANT CHANGE rows, re-prompt: "Confirming the significant change to `<X>` — proceed?"

### Step 2.4 — Draft and present the plan

- [ ] Invoke the `task-planner` skill to draft the plan.
- [ ] Write a plan that explicitly references each acceptance criterion from the ticket.
- [ ] Plan must include:
  - Existing implementation summary (from 2.1)
  - Edge case list (from 2.2)
  - `SIGNIFICANT CHANGE` rows if any (from 2.3)
  - Files to modify
  - Test strategy
  - **Architecture survey result** (from `develop-feature` Phase 1 Step 5a)
  - **Commit granularity** (default `one commit per logical change`, or per user instruction)
- [ ] Present the plan to the user and wait for explicit approval. Mandatory — do not proceed without "go ahead" or equivalent, and confirm significant changes separately per 2.3.
- [ ] Record the start time for the TIME_LOG entry in Phase 7.

## Phase 3 — Branch and transition

- [ ] Derive the branch name using the pattern from `JIRA_WORKFLOW.md`. Default is
      `{key}-{slug}` where `slug` is the kebab-cased ticket title.
- [ ] Invoke the `git-flow` skill to create and check out the branch.
- [ ] If `JIRA_WORKFLOW.md` has auto-apply enabled for the "work started" event:
  - [ ] Call `getTransitionsForJiraIssue(key)` to confirm the configured target
        status is reachable from the current status.
  - [ ] Call `transitionJiraIssue` to move the ticket to the configured "work
        started" status.
  - [ ] Call `addCommentToJiraIssue` with: "Started work. Branch: `{branch_name}`".

## Phase 4 — Implement

- [ ] Hand off to the `develop-feature` workflow starting at its Phase 2, passing:
  - The ticket's acceptance criteria.
  - The linked Confluence spec content (if any).
  - The plan approved in Phase 2.
- [ ] Implement and test following the standard `develop-feature` flow (code,
      tests, verification).

## Phase 5 — PR

- [ ] Invoke the `git-flow` skill to open a PR with title `[PROJ-1234] short description`
      (substituting the real ticket key and a concise description).
- [ ] PR body must include:
  - A link back to the Jira ticket.
  - A link to the linked Confluence spec, if any.
  - A summary of changes.
  - A test plan (either commands run or steps for a reviewer).
- [ ] If `JIRA_WORKFLOW.md` has auto-apply enabled for the "PR opened" event:
  - [ ] Call `transitionJiraIssue` to the configured "in review" status.
  - [ ] Call `addCommentToJiraIssue` with: "PR opened: `{pr_url}`. Ready for review."

## Phase 6 — Merge follow-up

This phase runs when the user says "PR PROJ-1234 merged" or similar, or via a
separate `post-merge-update` workflow.

- [ ] If `JIRA_WORKFLOW.md` has auto-apply enabled for the "PR merged" event:
  - [ ] Call `transitionJiraIssue` to the configured "ready for QA" status.
- [ ] If handoff rules say reassign on merge:
  - [ ] Look up the QA owner for this module from `.memory/TEAM.md` — match by
        ticket labels or by changed module path.
  - [ ] Call `editJiraIssue(key, assignee={qa_owner_account_id})` to reassign.
  - [ ] Call `addCommentToJiraIssue` with: "Merged. Handed off to
        `{qa_owner_name}`. Test scenarios: `{summary}`".
- [ ] If handoff rules are disabled, leave the assignee unchanged and only
      transition the status.

## Phase 7 — Task completion

- [ ] Invoke the `task-completion` skill to update CHANGELOG, TIME_LOG, and
      RESUME.md, and to commit the `.memory/` changes.
- [ ] In the CHANGELOG entry, include the ticket key (e.g. `[PROJ-1234]`) in the
      header or description.
- [ ] In the TIME_LOG entry, include the ticket key so time can be attributed back
      to the Jira ticket later.

## Final Step — Task Completion Checklist

Before responding to the user or starting the next task, run the Task Completion Checklist
from `core-behavior.md`. This is not optional.
